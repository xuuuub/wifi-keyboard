# 技术文档 — 手机当键盘

> 版本：v1.0
> 更新日期：2026-10-07
> 适用代码：`server.py` / `static/index.html` / `static/style.css` / `static/script.js`

---

## 1. 项目定位

把手机变成一个**远程键盘**：手机浏览器里打字，文字实时出现在电脑**当前光标**处。

不依赖任何第三方服务，不走公网。手机和电脑在同一个局域网内即可工作。

---

## 2. 系统架构

### 2.1 拓扑

```
┌─────────────┐        局域网 / USB 隧道         ┌──────────────────┐
│   手机       │  ───────────────────────────▶  │   电脑            │
│  浏览器      │      HTTP  :8765  (页面/资源)   │   server.py       │
│  index.html │      WS    :8765  (JSON 消息)   │   aiohttp         │
│  style.css  │                                 │        │          │
│  script.js  │  ◀───────────────────────────  │        ▼          │
└─────────────┘           无回传数据             │   SendInput()     │
                                                │        │          │
                                                │        ▼          │
                                                │   操作系统输入队列  │
                                                │        │          │
                                                │        ▼          │
                                                │  当前前台窗口光标处 │
                                                └──────────────────┘
```

### 2.2 为什么这个架构能"出现在光标处"

关键点：**我们没有自己去写字符到某个文本框，而是把事件注入到操作系统的输入系统**。

Windows 的 `SendInput` API 注入的按键，和真实键盘敲出来的按键，在系统看来**完全一样**。系统会按正常流程把它派发给当前拥有焦点的窗口。所以：

- 当前焦点在 Word → 字进 Word
- 当前焦点在 VSCode → 字进 VSCode
- 当前焦点在浏览器地址栏 → 字进地址栏
- 电脑锁屏 → 字进锁屏密码框

**电脑端不需要知道任何"目标应用"的信息，也不需要适配任何软件**，这是整个方案最核心的设计决策。

## 3. 数据流

一次按键的完整链路：

```
1. 用户在手机 textarea 输入 "你"
2. 触发 input 事件 → sync()
3. 计算 diff：sent="" , cur="你" → del=0, ins="你"
4. WebSocket 发送 {"type":"text","data":"你"}
5. 服务端 handle_message() 收到 → type_text("你")
6. type_text 逐字符 → ord("你")=0x4F60 ≤ 0xFFFF
7. _send(KEYEVENTF_UNICODE down, KEYEVENTF_UNICODE up)
8. 电脑当前光标处出现"你"
9. 本地 sent 更新为 "你"
```

## 4. 通信协议

### 4.1 传输层

- **HTTP**：`GET /`（页面）、`GET /static/*`（资源）
- **WebSocket**：`GET /ws`，全双工，但**实际只用了单向**（手机 → 电脑）
- 端口默认 `8765`，HTTP 与 WS 共用

### 4.2 鉴权

URL query 参数 `t`，例如 `http://192.168.1.5:8765/?t=aB3xK9`。

**设计取舍：静态资源不校验 token，`/` 和 `/ws` 校验。**

理由：`style.css` / `script.js` 里没有任何敏感信息，真正的数据通道是 WebSocket。如果静态资源也要求 token，就必须把 token 拼进 `href`/`src`，得不偿失。安全性没有下降——攻击者拿到 CSS 也做不了任何事。

### 4.3 消息格式

所有消息是 JSON 文本帧。客户端 → 服务端：

| type | 字段 | 说明 |
|---|---|---|
| `text` | `data: string` | 注入一段文本（支持中文、emoji） |
| `key` | `key: string`<br>`count?: number` | 按一个特殊键，`count` 默认 1（用于连按退格） |
| `combo` | `mods: string[]`<br>`key: string` | 组合键，如 `{mods:["ctrl"], key:"s"}` |

服务端 → 客户端：**无应用层消息**（仅 WebSocket 协议的 ping/pong 心跳，`heartbeat=30`）。

### 4.4 校验与容错

服务端对每条消息独立做防御（`server.py:194-208`）：

- 非 TEXT 帧直接跳过
- JSON 解析失败静默跳过
- **单条消息处理异常只打日志，不断开连接**（这样一条脏数据不会让用户重连）
- `text` 的 payload 必须是非空 `str`
- `key` 的 `count` 被钳制在 `[1, 200]`，防止恶意构造导致长时间阻塞

## 5. 服务端实现

### 5.1 Win32 `SendInput` 结构体布局

`server.py:42-90`

`SendInput` 的 `INPUT` 结构体里是一个 **union**，包含 `KEYBDINPUT` / `MOUSEINPUT` / `HARDWAREINPUT`。

**必须把三个成员都完整定义出来**，因为 `dwSize` 参数要求传入 `sizeof(INPUT)`，而 union 的大小由最大的成员决定（64 位下为 24 字节）。如果只定义 `KEYBDINPUT`，union 会变小，`SendInput` 会因 `cbSize` 不匹配而直接返回 0（且不报错）——这是最常见的踩坑点。

```python
class INPUT(ctypes.Structure):
    _anonymous_ = ("u",)
    _fields_ = (("type", wintypes.DWORD), ("u", _INPUTUNION))
```

`_anonymous_` 让调用处可以直接写 `inp.ki` 而不用 `inp.u.ki`。

### 5.2 文本注入：为什么用 `KEYEVENTF_UNICODE`

两种注入方式对比：

| 方式 | 做法 | 问题 |
|---|---|---|
| 虚拟键码 | 把字符映射成 VK 码 | 只能覆盖键盘上有的键，中文、emoji 无解；且会**触发电脑的输入法**，中文会变成拼音字母 |
| `KEYEVENTF_UNICODE` | 直接把 Unicode 码点交给系统 | 任意字符都能注入，且**完全绕开输入法** |

我们选后者。这是中文能正常工作的根本原因。

```python
_send(_ki(scan=u, flags=KEYEVENTF_UNICODE),
      _ki(scan=u, flags=KEYEVENTF_UNICODE | KEYEVENTF_KEYUP))
```

**BMP 之外的字符**（如 emoji，码点 > 0xFFFF）需要手工拆成 UTF-16 代理对（`server.py:146-156`）：

```python
code -= 0x10000
units = [0xD800 + (code >> 10), 0xDC00 + (code & 0x3FF)]
```

### 5.3 换行与制表符的特殊处理

`server.py:159-168`

`\n` 和 `\t` **不走 Unicode 注入，而是走真实按键**（`VK_RETURN` / `VK_TAB`）。

原因：不同控件对"Unicode 注入的 `\n`"处理不一致——有的会插入一个换行符，有的毫无反应。而真实回车键在所有控件里行为都正确（表单里会提交、编辑器里会换行、聊天框里会发送）。

同时统一换行符：`\r\n` → `\n`、`\r` → `\n`，避免手机上粘贴 Windows 风格文本时多出空行。

### 5.4 虚拟键码与扩展键标志

`server.py:93-105`

```python
EXTENDED = {"delete", "left", "up", "right", "down", "home",
            "end", "pageup", "pagedown", "insert"}
```

这 9 个键在 Windows 上属于**扩展键**，必须带 `KEYEVENTF_EXTENDEDKEY`（0x0001）。

不加会怎样：方向键和数字键盘上的方向键虚拟码相同，系统靠扩展位区分。不加标志，注入的方向键在小键盘被选中的场景下会错乱。

### 5.5 组合键的按下/松开顺序

`server.py:131-143`

顺序必须是：**修饰键全部按下 → 主键按下 → 主键松开 → 修饰键逆序松开**。

实测教训：如果顺序反了（比如先按 S 再按 Ctrl），目标应用收到的就是"先输入 s，再单独按下 Ctrl"，`Ctrl+S` 完全失效。

### 5.6 网络探测与 URL 生成

`server.py:233-304`

打印给用户的 IP 从三个来源合并去重：

1. **默认路由地址**：`socket.connect(("8.8.8.8", 80))` 不实际发包，但内核会选好出口网卡，取 `getsockname()` 即得到"当前联网那张卡"的地址
2. **`ipconfig` 解析**：能拿到 `getaddrinfo` 漏掉的网卡，**尤其是 Windows 移动热点的 `192.168.137.1`**（这张虚拟网卡通常不注册到 DNS，第 1 步也拿不到）
3. **`getaddrinfo(hostname)`**：兜底

排序规则 `_rank()`：移动热点地址排最前，其次当前联网网卡，`192.168.144.*` / `192.168.56.*` 等**虚拟机虚拟网卡垫底且降权**（否则 Hyper-V 的 `192.168.144.1` 会排到真实网卡前面，用户照着访问必然失败）。

## 6. 前端实现

### 6.1 实时 diff 同步算法

`script.js` 的 `sync()` 是整个前端最核心的部分。

**问题**：手机输入框的变化是"整串字符串"，而电脑端只能通过按键来复现变化。如果每次变化都"全选+重打"，会造成大量无意义的按键。

**做法**：维护一个 `sent` 变量 = "我们认为电脑端当前已有什么"。每次输入后对比 `sent` 和当前值，算出**最小变更**：

```js
// 1. 求最长公共前缀 p
while (p < cur.length && p < sent.length && cur[p] === sent[p]) p++;

// 2. 求最长公共后缀 s（不与前缀重叠）
while (s < cur.length - p && s < sent.length - p &&
       cur[cur.length - 1 - s] === sent[sent.length - 1 - s]) s++;

// 3. 中间的部分就是变化量
const del = sent.length - p - s;              // 要删几个字符
const ins = cur.substring(p, cur.length - s); // 要插入什么
```

然后**先发退格、再发文本**：

```js
if (del > 0) send({ type: 'key', key: 'backspace', count: del });
if (ins) send({ type: 'text', data: ins });
sent = cur;
```

这样在手机上删字，电脑上也会同步删字，手感接近真键盘。

**已知局限**：算法假设"变更发生在串尾"（即用户从后往前编辑）。如果用户把光标移到中间插入字符，前后缀比对会把中间的差异算成一次巨大的删除+插入，电脑端表现会错乱。彻底的解法是改用基于 `selectionStart` 的精确 diff，属于待改进项。

### 6.2 输入法（IMF）处理

**问题**：中文用拼音输入时，`input` 事件会在**候选阶段**就反复触发，此时 `textarea.value` 里是未确定的拼音（如 `nihao`）。如果直接同步，电脑上会先出现一堆拼音字母，用户选字后又全部删掉重打。

**做法**：用 `compositionstart` / `compositionend` 屏蔽候选阶段：

```js
ta.addEventListener('compositionstart', () => { composing = true; });
ta.addEventListener('compositionend', () => {
  composing = false;
  if (realtimeEl.checked) sync();     // 只在"选定汉字"后才同步
});
ta.addEventListener('input', () => {
  if (composing) return;              // 候选阶段直接忽略
  if (realtimeEl.checked) sync();
});
```

效果：电脑上只会出现**最终选定的汉字**，中间过程完全不发送。

### 6.3 焦点保持（避免软键盘闪烁）

手机上一旦某个可聚焦元素获得焦点，软键盘会收起再弹出，体验极差。所以所有功能性按钮都拦截 `pointerdown`：

```js
b.addEventListener('pointerdown', (e) => e.preventDefault());
```

`pointerdown` 的默认行为会触发兼容性 `mousedown`，进而转移焦点。拦截掉之后，textarea 保持焦点，软键盘不闪。

**副作用**：`preventDefault` 同时会抑制 `:active` 状态的触发（Chrome 行为），所以这些按钮**按下时没有视觉高亮反馈**。属于已知取舍，待改进项。

### 6.4 断线重连

`script.js` 的 `connect()`

```js
ws.onclose = () => {
  ready = false;
  setStatus('已断开，重连中…', false);
  retry = Math.min(retry + 1, 10);
  setTimeout(connect, 500 * retry);   // 退避：0.5s → 5s 封顶
};
```

递增退避，最长 5 秒一次，避免手机切后台回来时疯狂重连打爆服务端。

### 6.5 布局要点

- `height: 100dvh`：动态视口高度，软键盘弹出时布局会自动收缩（`100vh` 在手机上不会）
- `env(safe-area-inset-*)`：适配刘海屏/挖孔屏/底部 Home 条
- `viewport-fit=cover` + 上面的 safe-area 配合才生效
- 按键区 `display: grid; grid-template-columns: repeat(4, 1fr)`：16 个键正好 4×4，无滚动
- `.float-clear` 用 `position: absolute` + `top: 50%` + `translateY(-50%)` 悬浮在文本区左侧，文本区用 `padding-left: 54px` 让位，保证正文不被遮挡

**三件套的加载关系**：

```html
<link rel="stylesheet" href="static/style.css">
<script src="static/script.js" defer></script>
```

- 用**相对路径**，页面在 `/?t=xxx`，相对路径按目录 `/` 解析为 `/static/style.css`
- `defer` 保证脚本在 DOM 解析完成后执行，所以 `script.js` 可以直接 `getElementById`
- 服务端必须有 `add_static("/static/", STATIC_DIR)` 路由，否则 404

## 9. 已知限制

| 限制 | 影响 | 原因 |
|---|---|---|
| 仅 Windows | 无法在 macOS/Linux 跑服务端 | 依赖 `SendInput`，是 Win32 专属 API |
| token 每次重启变化 | 手机需重新扫码 | 未做持久化 |
| 仅支持串尾编辑 | 光标移到中间改字会错位 | diff 用前后缀比对近似 |
| 不区分客户端 | 多台手机同时连会串 | `clients` 是集合，消息无来源标识 |
| 无速率限制 | 恶意客户端可高频注入 | 未做限流 |
| 依赖 Ctrl 等修饰键的文字描述 | 只支持预设的那些组合 | 前端按钮是硬编码列表 |
| 二维码在非 UTF-8 终端不显示 | 只影响终端展示 | `qrcode` 用了 `\u2580` 半方块字符，GBK 无法编码（已加 try/except 兜底，不影响服务启动） |
| 按键按下无高亮反馈 | 手感偏"没反应" | `pointerdown` 的 `preventDefault` 抑制了 `:active` |

## 10. 调试要点

**分层排查**，能快速定位问题在哪一层：

1. **电脑本机**：打开 `http://127.0.0.1:8765/?t=<token>`。能出页面且状态点变绿 → 服务端和前端都正常，问题在网络链路
2. **网络链路**：从手机访问 `http://<电脑IP>:8765/?t=<token>`。转圈/无法访问 → 防火墙或客户端隔离
3. **注入层**：页面能连上但电脑不出字 → 看终端有没有 `[+] 已连接`；有连接但不出字，检查注入逻辑

**网络链路的两个典型故障**：

- **防火墙**：网络配置文件为「公用」时入站默认丢弃。放行命令：
  ```powershell
  netsh advfirewall firewall add rule name="PhoneKeyboard" dir=in action=allow protocol=TCP localport=8765
  ```
- **客户端隔离**：校园网/公共 Wi-Fi 常开 AP 隔离，同 SSID 也互相不通。**这是防火墙之外的问题，放行防火墙无效**。解法见《未来计划》的网络部分
